# Identity, Authorization, and Tokens

**Status:** Reconciled implementation specification  
**Baseline:** Mentora Architecture Baseline 1.0  
**Purpose:** Specify principals, roles, and token validation.

## Dependencies

- `docs/architecture/17_SECURITY_PRIVACY_AND_GOVERNANCE.md`

## Normative Language

**MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are requirements. Technology choices explicitly marked `PROPOSED` are not binding until accepted.

---

Users authenticate through institutional federation; services use workload identity. Roles: platform/institution admin, IT operator, course admin, teacher, moderator, student, auditor. Every request validates tenant/course/class/resource. Normal student media permission is subscribe-only. Floor token independently binds class/room/student/request/floor/epoch/state/nonce/expiry and publish_audio only. Key rotation overlaps safely; revocation failure denies new publication.

## Implemented identities and authorization (V0-021)

Implemented in `backend/app/identity/` (the domain), `backend/app/providers/local_credentials.py` (the one registered credential adapter) and `backend/app/api/security.py` (the request-time enforcement). The frontend half is `frontend/src/auth/`.

**The credential mechanism is NOT a decided technology.** The paragraph above — institutional federation — is the canonical requirement; every entry in `governance/DECISION_LEDGER.yaml` about an identity provider, token format or federation protocol is `OPEN`/`PROPOSED`, and no ADR accepts one. `FND-002` is still `TODO`. So, exactly as with the voice capability (`DEC-TECH-007`) and the renderer (`DEC-TECH-005`), the implementation is the **provider-neutral interface plus an explicitly-labelled stand-in**, and the stand-in says so in the response (`authenticator.kind: DEVELOPMENT_MOCK`) and in `GET /auth/me`. Nothing here may be presented as the platform's authentication.

The seam is `app/identity/port.py::Authenticator` — `authenticate(institution_id, email, credential) -> AuthenticatedSubject | None`, `provision_credential(institution_id, account, secret) -> bool`, plus an `identity` property naming the capability. An OIDC/OAuth adapter is a second implementation of that ABC; no domain code changes when it arrives (the adapter depends on the port, never the reverse, enforced by the same layering rule the speech domain uses). The registered adapter is `local-credentials@1.0.0` (`app/providers/factory.py::create_authenticator`): stdlib `hashlib.scrypt` with a per-account random salt, **digest-only** storage, and a constant dummy-salt verification on an unknown address so a missing account and a wrong credential take the same time and are indistinguishable. `provision_credential` **stores** a secret the caller supplies (V0-023); it never mints or returns one. A federation adapter would own the secret entirely — that is the behaviour it would remove — so the secret is the administrator's or the holder's, chosen and never echoed back.

**The tenant is a session claim, never a request field.** `POST /auth/login` resolves the account in the institution named in its **body** (that is what the credential proves); every later request derives `institution_id` from the session `app/api/security.py` resolves, and the API ignores `X-Institution-Id` when a session is present. A session therefore cannot be widened by anything a caller names. Only the token's SHA-256 digest is stored (`auth_sessions.token_sha256`); the raw token exists once, in the login response. Claims and their invariants are contracted in `contracts/security/session-claims.schema.json`.

**Capabilities, not role names.** `Scope` (`app/identity/models.py`) is the unit of authorization and `ROLE_SCOPES` is the single place a role's capabilities are decided, so a role can never accumulate a capability because an endpoint forgot to check. Guards are written against a *missing capability* (`app/api/security.py::require(scope)`), and every route verb on every router carries one. A request without a principal is `401 UNAUTHENTICATED` (`issue_code SESSION_REQUIRED`); a principal without the scope is `403 INSUFFICIENT_SCOPE` (`issue_code SCOPE_REQUIRED`) — both stable codes, distinct from `AUTHENTICATION_FAILED` (`401`, a credential the mechanism rejected) and `AUTHENTICATION_UNAVAILABLE` (`503`, the capability could not be reached — an availability failure, never a denial, `DEC-RELIABILITY-002`).

**Session scopes are re-derived, not remembered.** A session row stores the scopes it was issued with and every read **intersects** them with what the account's role currently grants. Narrowing a role therefore takes effect on the account's next request rather than at session expiry, and revoking a session is a `revoked_at` write the same read honours (`DEC-RUNTIME-007`). The intersection can only ever *remove*: widening a role takes effect on the account's next sign-in, because a role edit must never retroactively hand a live session a capability it was never issued.

**Three roles are modelled**, as of V0-022: `institution_admin`, `teacher` and `student`. The spec's wider list (platform admin, IT operator, course admin, teaching assistant, moderator, auditor) is still **not** modelled, and the enum in the session-claims schema says so rather than implying it exists. `student` is exactly *"attend the class"*: `class:read`, `scene:read`, `join` — nothing that writes. A student on a teacher verb is refused by the guard, not by a page choosing to hide a button.

The reciprocal also holds, as a capability rather than a role test: `join` is the **participant** capability, so it belongs to the student role alone and a teacher holds none. That is "a teacher token is refused where student identity is required" in practice — a teacher principal asking for a join credential is refused `403 INSUFFICIENT_SCOPE` (`SCOPE_REQUIRED`) at the guard, before any class is read. A teacher's access to a class is the classroom session (`class:read` plus the Actor), not a seat in it.

**Enrolment is the class-scoped authorization.** A join is authorized by the *pair*: the class is `ACTIVE` **and** the caller's own account is enrolled in it, in the caller's own tenant (`403 NOT_ENROLLED` otherwise; a class of another institution is `TENANT_ACCESS_DENIED`). `POST /classes/{id}/bootstrap-token` takes **no body** — there is no student id in the request, so the credential is bound to the session's account and a caller cannot ask for someone else's join. It carries `subscribe` scope only (`DEC-TURN-001`) and binds class/student/session/`actor_epoch`/nonce/expiry (`DEC-RUNTIME-007`). Only its SHA-256 digest is stored. The roster is other people's identities, so *listing* it is a teacher capability (`enrollment:write`); a student's own enrolment is reported by the join check and `GET /classes/{id}`, never by the roster list. **Enrolment never creates an account** (V0-022): an address this institution has no account for is `404` (`issue_code ACCOUNT_REQUIRED`), because creating identities and assigning them are different jobs — see below.

**What the class is shown is what it pinned.** `GET /classes/{id}/scenes` and `GET /classes/{id}/scenes/{order}` resolve the session's own `RuntimeSessionPlan` — never the course's current publication — so a correction published mid-lesson changes nothing a student sees (`DEC-CONTENT-005`). The render is served **through the package manifest** (a path the manifest does not list is not readable, so this cannot become an arbitrary object read) and every served file is re-checked against the digest the manifest recorded: a file swapped in storage is refused with `502 STORAGE_FAILURE` (`issue_code SCENE_CHECKSUM_MISMATCH`) rather than presented. A request that has no session reads nothing.

**The development tenant shortcut is off by default (V0-023).** `Settings.dev_tenant_header` (`MENTORA_DEV_TENANT_HEADER`, default **off**) is the one pre-auth path: with it explicitly switched on and a valid `X-Institution-Id` but no session, a request resolves a **teacher** principal marked `authenticated: false` with **no account**. It exists only as a developer opt-in and is never presented as a sign-in. It is off by default so that **every route requires a real session** out of the box; turning it on is a deliberate, development-only decision, and the client learns which state it is in by asking `GET /auth/me` (a `401 SESSION_REQUIRED` when the shortcut is off) rather than assuming. Even when on, the shortcut cannot join a class — it *is a teacher*, and `join` is the student's participant capability: the guard refuses it `403 INSUFFICIENT_SCOPE` before the class is read. (Having no account is a second, independent reason: a join credential binds to the authenticated student's own account.)

## Implemented administration and role separation (V0-022)

V0-022 splits the two jobs an account system performs, so that neither is implied by the other: **administering the directory** (who exists) is the institution administrator's, and **assigning people to a class** (who attends) is the teacher's. It also gives each of the three roles the same sign-in surface, because who you are is the account's role and not a choice on a page.

**`institution_admin` is a real role with the smallest set that does its job.** `ROLE_SCOPES[institution_admin]` is `{account:read, account:write, content:read, class:read}` — the directory, plus read-only institution-wide oversight, plus **nothing else**: no authoring (`content:write`, `review:write`, `publication:write`), no roster (`enrollment:write`), no participant capability (`join`) and no scene read (`scene:read`). An administrator is not a super-teacher; the checks are the same `require(scope)` guards as every other verb, and the two new capabilities (`account:read`, `account:write`) are the only ones added.

**A teacher reads the students, not the staff.** `teacher` gains `account:read`, but the *list* is restricted: `GET /accounts?role=` requires the role explicitly (so it can never become an accidental directory dump) and a caller without `account:write` gets `403 INSUFFICIENT_SCOPE` (`SCOPE_REQUIRED`) for any role outside `TEACHER_LISTABLE_ROLES = {student}` — the same rule on `GET /accounts/{id}` for the account's own role. So a teacher can populate a roster picker and cannot read a colleague. That is a deliberate narrowing of an otherwise-institution-wide capability, enforced in `app/api/accounts_router.py`.

**Separation of duties, and where it is enforced.** `MANAGEABLE_ROLES = {teacher, student}`: an administrator creates teachers and students, and **cannot create or change another administrator** (`409`, `issue_code ROLE_NOT_MANAGEABLE`) — an administrator cannot multiply itself. The institution's **first** administrator comes from a one-shot deployment bootstrap, `POST /auth/bootstrap-admin`, which is unauthenticated by necessity (there is no administrator yet to authorize it), gated on its **own** setting `Settings.admin_bootstrap` (`MENTORA_ADMIN_BOOTSTRAP`, default on — V0-023 moved it off the tenant-header switch, so a locked installation can still create its first account; `404`, `issue_code BOOTSTRAP_DISABLED` when off), and refuses the moment the tenant has an administrator (`409`, `issue_code TENANT_ALREADY_PROVISIONED`) without writing anything. Under institutional federation the identity provider provisions that account, which is why this is a development seam and not the platform's account-creation path.

**Creating is create-or-link and never re-mints a secret.** The same address and role returns the existing account with `created: false` and `credential_set: false`, so a retried create cannot overwrite the password the holder set (`DEC-RUNTIME-003`); the same address with a *different* role is `409` (`issue_code EMAIL_ROLE_CONFLICT`) rather than a silent role change, and an unknown role name is `400 INVALID_REQUEST` — a refusal the caller can act on, kept apart from a policy conflict.

**A disable or a password reset is a revocation.** `PATCH /accounts/{id}` with `status: DISABLED` revokes the account's live sessions in the **same** call (`DEC-RUNTIME-007`) and reports how many (`sessions_revoked`), so a disabled account stops working on its next request rather than at expiry — and a fresh sign-in is refused while it is disabled. Re-enabling restores sign-in with the credential the account already had. Setting or resetting the account's `password` revokes its live sessions for the same reason: a credential change that left other sessions working would not really have changed who can get in. A **role change** is the deliberate opposite: it can only ever *remove* a capability from a live session, because the session's stored scopes were intersected with the role that issued them; a promotion takes full effect at the account's next sign-in.

**An identity that a class used is deactivated, not deleted.** `DELETE /accounts/{id}` refuses an account referenced by any class roster in the tenant (`409 CONFLICT`, `issue_code ACCOUNT_IN_USE`) and the remedy is `PATCH status=DISABLED`; use is read through `ClassroomService.enrolled_anywhere`, composed in the API layer so the identity domain never learns about classrooms. An unreferenced account is removed together with its credential material and sessions, in one transaction. Removal is guarded rather than cascading because a cascading delete would silently empty rosters a session's history refers to.

**Unassigning is a roster correction, not an account change.** `DELETE /classes/{id}/enrollments/{studentId}` (idempotent, `enrollment:write`) ends the ability to obtain a **new** join credential immediately — the join check reads this roster — while the account, its sessions and any credential it already holds are untouched, each with its own epoch and expiry (`DEC-RUNTIME-007`). The route is refused for a caller without `enrollment:write` before the student id is even read.

Every one of these verbs is tenant-scoped from the **session**, so an administrator of one institution can neither read nor write another's directory: an account of the other tenant is `403 TENANT_ACCESS_DENIED`, and `X-Institution-Id` alongside a session changes nothing. Telemetry records the activity as identities and outcomes — an event carries the address's *presence* plus `subject_digest(subject)`, never the address itself.

## Required sign-in and password credentials (V0-023)

V0-023 changes *which credential a subject presents* and *who may reach a page*. It does **not** decide the credential mechanism — the adapter is still a labelled development mock — but it closes the platform behind a sign-in and gives every account a password.

**Nothing is reachable without a session.** With the shipped defaults (`MENTORA_DEV_TENANT_HEADER` off) a request carrying only `X-Institution-Id` is `401 UNAUTHENTICATED` (`issue_code SESSION_REQUIRED`) on every route. The only routes that answer without a session are `/health`, `/auth/login` (which refuses a bad password as `401 AUTHENTICATION_FAILED` rather than `401 SESSION_REQUIRED`, because presenting a credential is the act of signing in) and `/auth/bootstrap-admin` while its own switch is on. `/auth/logout` is deliberately callable with an already-expired token, because signing out must never fail.

**A password replaces the one-time code.** `POST /auth/login` takes `password`; the administrator sets an initial password when creating an account (`POST /accounts`) and can reset it (`PATCH /accounts/{id}` with `password`); the account holder can change their own (`POST /auth/password`, which verifies the current password exactly as a sign-in does). A password **too short** is `400 INVALID_REQUEST` (`issue_code CREDENTIAL_TOO_WEAK`); `MIN_CREDENTIAL_LENGTH = 8` is documented as a **development guard, not a decided password policy** (`FND-002` is `TODO`). A wrong current password on a change is `401 AUTHENTICATION_FAILED` (`issue_code INVALID_CREDENTIALS`) and the caller's session stays valid, because a mistyped field is not a sign-out.

**A password is a body, never a query string.** `POST /auth/bootstrap-admin`, `POST /accounts` and `PATCH /accounts/{id}` carry the secret in a JSON body: a password in a URL would be written to access logs and browser history. The request bodies are contracted in `contracts/openapi/openapi.yaml` (`LoginRequest`, `AccountCreateRequest`, `AccountUpdateRequest`, `BootstrapRequest`, `PasswordChangeRequest`).

**A self-service change revokes the others and keeps the caller's.** `POST /auth/password` re-provisions the account's digest and revokes every *other* live session, so a change really does change who can get in; the session that asked is kept, so the person is not thrown out of the page they are on.

**The frontend is behind the same rule.** Every page except `/login` renders the sign-in form until a session exists, remembering the page it was headed to (`?next=`) and returning there afterwards; the redirect is `replace`, so a guarded path does not linger in the history, and `/login` itself is never put in `?next`. A `401` that means the server no longer accepts the session (expired, revoked, unknown, disabled) drops the stored session, so the guard re-applies with a truthful state rather than a page that only `401`s. `hasScope(null, …)` is `false` for every scope: **no session is no capabilities**, and the authoring entries are absent rather than merely disabled. The development-mode affordance was removed from the client entirely.
